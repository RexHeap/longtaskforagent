# Long-Task Agent Architecture

## Core Concept

Long-running tasks exceed a single context window. The solution: split work into an **Initializer Session** (runs once) and multiple **Worker Sessions** (run iteratively), connected by persistent artifacts on disk.

## Persistent Artifacts

### 1. `task-progress.md`

Session log that bridges context gaps. Each worker session appends an entry.

```markdown
# Task Progress Log

## Project: [name]
Created: [date]

---

### Session 1 — [date/time]
**Focus**: User authentication API endpoints
**Completed**:
- POST /auth/login with JWT
- POST /auth/register with validation
- Unit tests for auth module (12/12 passing)
**Issues**: None
**Next Priority**: Password reset flow (feature #5)
**Git Commits**: a1b2c3d, e4f5g6h
```

### 2. `feature-list.json`

Structured task inventory. JSON format prevents accidental model corruption.

```json
{
  "project": "project-name",
  "created": "2025-01-15",
  "features": [
    {
      "id": 1,
      "category": "core",
      "title": "User login with JWT",
      "description": "POST /auth/login returns JWT token on valid credentials",
      "priority": "high",
      "status": "passing",
      "verification_steps": [
        "Send POST with valid credentials, verify 200 + token",
        "Send POST with invalid credentials, verify 401",
        "Verify token contains correct claims"
      ],
      "dependencies": []
    },
    {
      "id": 2,
      "category": "core",
      "title": "User registration",
      "description": "POST /auth/register creates new user account",
      "priority": "high",
      "status": "failing",
      "verification_steps": [
        "Send POST with valid data, verify 201",
        "Send POST with duplicate email, verify 409",
        "Verify password is hashed in DB"
      ],
      "dependencies": []
    }
  ]
}
```

**Rules**:
- Status is only `"failing"` or `"passing"` — never `"partial"` or `"in-progress"`
- Never remove or edit verification_steps — only change `status`
- Features marked `"passing"` must be re-verified at session start

### 3. `init.sh` / `init.ps1`

Deterministic environment startup script. Created by the initializer, used by every worker session.

```bash
#!/bin/bash
# init.sh — project environment bootstrap
cd "$(dirname "$0")"

# Install dependencies
npm install 2>/dev/null || pip install -r requirements.txt 2>/dev/null

# Start services
docker-compose up -d 2>/dev/null

# Start dev server (background)
npm run dev &
# or: python manage.py runserver &

echo "Environment ready."
```

### 4. `RELEASE_NOTES.md`

Living document that tracks all user-visible changes. Updated after **every git commit** to ensure release notes stay in sync with code.

```markdown
# Release Notes

## [Unreleased]

### Added
- User login with JWT authentication (#1)
- User registration with email validation (#2)

### Changed
- (none yet)

### Fixed
- (none yet)

---

## [0.1.0] — 2025-01-15
### Added
- Initial project scaffold
```

**Rules**:
- Use [Keep a Changelog](https://keepachangelog.com/) format: Added, Changed, Deprecated, Removed, Fixed, Security
- Reference feature IDs from `feature-list.json` in each entry
- Move entries from `[Unreleased]` to a versioned section when milestones are reached
- Update immediately after each git commit — never defer to end of session

### 5. Git History

- Each session commits with descriptive messages
- Enables reverting broken changes
- Provides context for subsequent sessions via `git log`

### 6. `long-task-guide.md`

Worker session guide generated by `init_project.py`. Contains the full Step 1-5 workflow for each context cycle. Lives in the project root.

### 7. `CLAUDE.md` (appended, not overwritten)

`init_project.py` appends a reference block to `CLAUDE.md`:
```markdown
<!-- long-task-agent -->
## Long-Task Agent
Read `long-task-guide.md` at the start of EVERY session and follow its instructions.
<!-- /long-task-agent -->
```

Because Claude Code auto-reads `CLAUDE.md` on startup, this ensures the agent automatically discovers `long-task-guide.md` after every `/clear`.

## Initializer Session Workflow

The initializer runs **once** at the start of a long task. Its job:

1. **Read requirement doc** — understand scope
2. **Read design doc** — understand architecture and tech stack
3. **Run `init_project.py`** — scaffolds `long-task-guide.md`, `CLAUDE.md` reference, `feature-list.json`, `task-progress.md`, `init.sh`/`init.ps1`
4. **Generate `feature-list.json`** — decompose requirements into 10-200+ verifiable features with priority ordering
5. **Customize `init.sh`/`init.ps1`** — for the project's tech stack
6. **Set up project skeleton** — directory structure, config files, package.json / pyproject.toml etc.
7. **Initial git commit** — establish baseline
8. **Verify environment** — run init script, confirm basic setup works

## Worker Session Workflow (Context Cycle)

Each worker cycle follows this exact sequence. After `/clear`, the agent re-enters at Phase 1 by reading `long-task-guide.md` (auto-discovered via `CLAUDE.md`).

### Phase 1: Orient (understand current state)
1. `pwd` — confirm working directory
2. Read `task-progress.md` — understand what happened before
3. Read `feature-list.json` — find next priority failing feature
4. `git log --oneline -20` — see recent commits
5. `git diff HEAD~3` — check recent changes if needed

### Phase 2: Bootstrap (restore environment)
6. Run `init.sh` / `init.ps1` — start dev server / services
7. Run smoke tests — verify previously-passing features still work

### Phase 3: TDD Red — write failing tests first
8. Pick the highest-priority `"failing"` feature whose dependencies are all `"passing"`
9. Write unit tests that cover the feature's `verification_steps` — tests MUST fail (no implementation yet)
10. If feature has UI: write Chrome DevTools MCP functional tests (snapshot, click, fill, screenshot assertions) — tests MUST fail

### Phase 4: TDD Green — implement to pass tests
11. Write minimal code to make ALL tests pass (unit tests + functional tests)
12. Run full test suite — confirm all new tests green, no regressions

### Phase 5: TDD Refactor — clean up
13. Refactor code while keeping all tests green
14. Run verification again — mark feature as `"passing"` in `feature-list.json` ONLY after ALL tests pass

### Phase 6: Persist (save state for next session)
15. `git add` + `git commit` with descriptive message
16. Update `RELEASE_NOTES.md` — add entry under `[Unreleased]` with feature title, ID, and change type
17. Append session entry to `task-progress.md`
18. Validate: `python scripts/validate_features.py feature-list.json`
19. Commit updated `task-progress.md`, `feature-list.json`, and `RELEASE_NOTES.md`

### Phase 7: Clear context and continue
20. If ALL features are `"passing"` → announce project completion and stop
21. Otherwise, tell user which feature is done and which is next
22. Execute `/clear`
23. After clear, send: `"Continue working on this project. Read long-task-guide.md for instructions."`

**Critical rule**: One feature per cycle. If context remains after one feature, pick the next. Never leave code in a broken state.

## Context Continuity Flow

```
Initializer → scaffold → populate features → commit → begin first Worker cycle
                                                            ↓
                                                    ┌─── Worker Cycle ───┐
                                                    │ Orient             │
                                                    │ Bootstrap          │
                                                    │ Implement (1 feat) │
                                                    │ Persist + commit   │
                                                    │ /clear             │
                                                    └────────┬───────────┘
                                                             │
                                            CLAUDE.md auto-read on startup
                                                             │
                                                    "Read long-task-guide.md"
                                                             │
                                                    ┌─── Worker Cycle ───┐
                                                    │       ...          │
                                                    └────────────────────┘
                                                    (repeat until all passing)
```

## Anti-Patterns to Avoid

| Anti-Pattern | Why It Fails | Correct Approach |
|---|---|---|
| Attempting all features at once | Context exhaustion mid-implementation, cascading failures | One feature per session |
| Declaring victory without testing | Features appear done but break in practice | Verify every feature through actual tests |
| Writing code before tests (skipping TDD Red) | Tests end up testing implementation rather than behavior; missed edge cases | Always write failing tests first, then implement |
| Skipping Chrome DevTools functional tests for UI | UI may render but not function correctly for users | Every UI feature needs snapshot/click/fill/screenshot verification |
| Not updating RELEASE_NOTES.md | Release notes drift from actual state; costly catch-up later | Update after every git commit |
| Editing verification_steps | Lowers the bar to match broken code | Steps are immutable once set |
| Skipping progress file update | Next session wastes tokens rediscovering state | Always update before ending session |
| Not committing at session end | Work may be lost, next session can't diff | Always commit working code |
| Using markdown for feature list | Models tend to corrupt/reformat markdown lists | Use JSON for structured data |

## Verification Strategy

### For ALL features (TDD mandatory):
1. **Red**: Write failing tests first — tests define the expected behavior
2. **Green**: Write minimal implementation to pass tests
3. **Refactor**: Clean up while keeping tests green

### For API / backend features:
- Unit tests for business logic (pytest, jest, etc.)
- Integration tests: make actual HTTP requests and check responses
- Verify database state when applicable

### For UI / frontend features (Chrome DevTools MCP required):
- Unit tests for component logic
- **Functional tests via Chrome DevTools MCP**:
  - `take_snapshot` — capture accessibility tree, verify expected elements exist
  - `click` / `fill` — simulate user interactions
  - `take_screenshot` — capture visual state for verification
  - `wait_for` — confirm dynamic content appears
  - `list_console_messages` — check for runtime errors
  - `evaluate_script` — assert DOM state programmatically
- Test flow: navigate → snapshot → interact → snapshot → assert expected state

### For data / pipeline features:
- Run with sample data and verify output
- Check edge cases explicitly
- Compare output against expected results

## TDD Workflow Detail

```
┌─── TDD Red ─────────────┐
│ 1. Read feature spec     │
│ 2. Write unit tests      │
│ 3. Write functional      │
│    tests (if UI)         │
│ 4. Run tests → ALL FAIL  │
└──────────┬───────────────┘
           ↓
┌─── TDD Green ───────────┐
│ 5. Write minimal code    │
│ 6. Run tests → ALL PASS  │
└──────────┬───────────────┘
           ↓
┌─── TDD Refactor ────────┐
│ 7. Clean up code         │
│ 8. Run tests → STILL     │
│    ALL PASS              │
│ 9. Mark "passing"        │
└──────────────────────────┘
```

### Chrome DevTools MCP Functional Test Pattern

For each UI feature, create a test sequence:
```
1. Navigate to relevant page:      navigate_page(url)
2. Capture initial state:          take_snapshot()
3. Verify expected elements:       check uid presence in snapshot
4. Perform user action:            click(uid) / fill(uid, value)
5. Wait for response:              wait_for(text)
6. Capture result state:           take_snapshot() / take_screenshot()
7. Assert expected outcome:        verify elements, text, or visual state
8. Check for errors:               list_console_messages(types=["error"])
```

## Release Notes Maintenance

### When to update `RELEASE_NOTES.md`:
- After **every** git commit that changes functionality
- Before clearing context (as part of Persist phase)

### Format (Keep a Changelog):
```markdown
## [Unreleased]

### Added
- Feature description (feature #ID)

### Changed
- What changed and why (feature #ID)

### Fixed
- Bug description (feature #ID)
```

### Categories:
- **Added**: new features
- **Changed**: changes to existing functionality
- **Deprecated**: soon-to-be removed features
- **Removed**: removed features
- **Fixed**: bug fixes
- **Security**: vulnerability fixes

# Long-Task Agent

Execute multi-session software projects by decomposing requirements into verifiable features, maintaining persistent state across sessions, and implementing one feature per context cycle.

## Workflow Overview

Three phases, connected by persistent artifacts on disk:

1. **Brainstorming** (before initialization) — Explore requirements, propose approaches, get design approval
2. **Initializer** (first session) — Decompose into features, scaffold project
3. **Worker** (every subsequent cycle) — Orient, bootstrap, implement one feature, review, persist

Determine which phase:
- **No `docs/plans/` design doc AND no `feature-list.json`?** → Run Brainstorming first
- **Design doc exists but no `feature-list.json`?** → Run Initializer
- **`feature-list.json` exists?** → Run Worker

## Phase 0: Brainstorming & Design

**Hard gate**: No feature decomposition, scaffolding, or coding until design is approved.

1. **Explore context** — Read requirement doc, design doc (if any), existing code
2. **Clarify requirements** — Ask user questions one at a time via `AskUserQuestion` for ambiguities
3. **Propose 2-3 approaches** — Each with explicit pros, cons, and "best when" conditions; include a recommendation
4. **Section-by-section approval** — Present architecture, data model, API design, UI/UX, testing strategy; wait for user approval per section (for simple projects: single combined approval)
5. **Write design document** — Save approved design to `docs/plans/YYYY-MM-DD-<topic>-design.md`
6. **Proceed to Initializer**

For detailed process, see [references/brainstorming.md](references/brainstorming.md).

## Phase 1: Initializer

Run once, after design is approved. Steps:

1. **Read the approved design document** from `docs/plans/`
2. **Run `scripts/init_project.py`** to scaffold all persistent artifacts:
   ```
   python <skill-dir>/scripts/init_project.py <project-name> --path <project-dir>
   ```
   Creates: `long-task-guide.md`, `feature-list.json`, `task-progress.md`, `RELEASE_NOTES.md`, `init.sh`, `init.ps1`
3. **Copy `scripts/validate_features.py`** into `<project-dir>/scripts/`
4. **Configure `tech_stack` and `quality_gates`** in `feature-list.json`:
   - Set `language`, `test_framework`, `coverage_tool`, `mutation_tool` for the project
   - Adjust `quality_gates` thresholds if needed (defaults: line 90%, branch 80%, mutation 80%)
5. **Decompose requirements into features** — Populate `feature-list.json` guided by the approved design:
   - Each feature: `id`, `category`, `title`, `description`, `priority` (high/medium/low), `status` (always `"failing"` initially), `verification_steps` (concrete, specific), `dependencies` (feature id array)
   - Aim for 10-200+ features; each independently verifiable and completable in one session
   - Order by priority and dependency chain
5. **Validate**: `python scripts/validate_features.py feature-list.json`
6. **Customize `init.sh` / `init.ps1`** for the tech stack
7. **Scaffold project skeleton** (dirs, configs, dependency manifests, `examples/` directory)
8. **Git init + initial commit**
9. **Run init script**, verify environment works
10. **Update `task-progress.md`** with Session 0 entry (include design doc reference)
11. **Begin first Worker cycle** (proceed to Phase 2)

## Phase 2: Worker

Each Worker cycle follows the steps in `long-task-guide.md` (generated by init_project.py). The cycle:

1. **Orient** — read `task-progress.md`, `feature-list.json`, `git log`; pick next failing feature
2. **Bootstrap** — run `init.sh`/`init.ps1`; smoke-test passing features
3. **Plan** — write a step-by-step implementation plan for the selected feature before coding; save to `docs/plans/` (see [references/plan-writing.md](references/plan-writing.md))
4. **TDD Red** — write failing tests FIRST: unit tests for all features; Chrome DevTools MCP functional tests for UI features
5. **TDD Green** — implement minimal code to make all tests pass
5a. **Coverage Gate** — run language-specific coverage tool; verify line >= 90%, branch >= 80%; if below, write more tests (see [references/coverage-and-mutation.md](references/coverage-and-mutation.md))
6. **TDD Refactor** — refactor while keeping tests green; run full verification
6a. **Mutation Gate** — run incremental mutation testing on changed files; verify score >= 80%; if below, improve assertions (see [references/coverage-and-mutation.md](references/coverage-and-mutation.md))
7. **Verify & Mark** — execute `verification_steps`, read FULL output, confirm ALL pass; mark `"passing"` ONLY with fresh evidence (see [references/verification-enforcement.md](references/verification-enforcement.md))
8. **Code Review** — run two-stage review: Stage 1 (spec compliance) → Stage 2 (code quality); fix Critical/Important issues before proceeding (see [references/code-review.md](references/code-review.md))
9. **Add Examples** — create/update usage examples in `examples/` to demonstrate the completed feature (granularity matches feature scope; optional for infrastructure-only features)
10. **Persist** — git commit (incl. examples); update `task-progress.md`; update `RELEASE_NOTES.md`; validate feature list; commit again
11. **Continue** — if failing features remain, proceed to the next feature; if context is exhausted, end the session

**On test failure or unexpected errors**: Follow the systematic debugging process — never guess-and-fix. See [references/systematic-debugging.md](references/systematic-debugging.md).

For detailed architecture, artifact formats, and anti-patterns, see [references/architecture.md](references/architecture.md).

## Critical Rules

- **Design before implementation** — run Brainstorming phase; no coding until design is approved
- **Never remove or edit `verification_steps`** — immutable once created
- **Never mark `"passing"` without fresh evidence** — run actual tests, read full output, confirm all green THEN mark (see [references/verification-enforcement.md](references/verification-enforcement.md))
- **Strict TDD** — always write failing tests before implementation code; never skip Red→Green→Coverage→Refactor→Mutation
- **Coverage gate after TDD Green** — run coverage tool, verify line >= 90%, branch >= 80% before proceeding
- **Mutation gate after TDD Refactor** — run incremental mutation testing, verify score >= 80%
- **Coverage before mutation** — always pass coverage gate first; mutation on uncovered code is wasteful
- **Incremental mutation for features, full at milestones** — diff-based per feature, full run at project milestones
- **Code review after every feature** — two-stage review (spec compliance → code quality) before Persist
- **Systematic debugging only** — no guess-and-fix; always trace root cause first (see [references/systematic-debugging.md](references/systematic-debugging.md))
- **UI features require Chrome DevTools MCP testing** — use `take_snapshot`, `click`, `fill`, `take_screenshot` etc. to verify UI behavior functionally
- **Add examples after each feature** — create runnable examples in `examples/` that demonstrate newly completed features; skip only for pure infrastructure features
- **Update `RELEASE_NOTES.md` after every git commit** — keep it in sync with project progress
- **JSON for feature list** — models corrupt markdown more easily
- **One feature per cycle** — prevents context exhaustion
- **Always commit + update progress + update release notes before ending session** — bridges context gap
- **Never leave broken code** — revert incomplete work

## Red Flags (Agent Rationalizations to Resist)

If you catch yourself thinking any of these, STOP and follow the correct process:

| Rationalization | Correct Response |
|---|---|
| "This is too simple for a design phase" | Run lightweight design (single approval step) |
| "I already know the best approach" | Present options, let the user choose |
| "The tests should pass" | Run the tests and read the output |
| "Let me just try this quick fix" | Follow systematic debugging — trace root cause first |
| "I'll add tests after" | TDD Red comes first — always |
| "This is too simple for code review" | At minimum run Stage 1 (spec compliance) |
| "It probably works" | "Probably" is a red flag — verify with evidence |
| "I'll skip the example for this one" | Only skip for pure infrastructure features |
| "I'll update release notes at the end" | Update after every commit |
| "Coverage looks fine" | Run the coverage tool and read the numbers |
| "Mutation score is probably OK" | Run mutation tests and read the report |
